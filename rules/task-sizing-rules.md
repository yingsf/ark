# Task Sizing Rules

本文件定义 ark 的任务规模判定规则，用于帮助选择合适的工作流强度。

## 默认规模假设

当没有足够上下文判断规模时，默认按 **medium** 处理，宁可轻微过度规划，不可草率执行。

流程说明中的 `intake` 只负责澄清、分流和建议落盘位置，不直接写入 `docs/ark/*`。规格、设计、计划、任务、验证、交接和决策的 Artifact 落盘必须由对应 Skill 完成。

当任务需要专题详细方案、接口契约、集成说明或数据源元信息时，使用 `/ark:ark-solution` 写入项目自有扩展文档；不要把这类正文塞入 `docs/ark/*`。

## 目标

在任务开始前，为 small / medium / large 提供更一致的判断标准，避免：

- 小题大做
- 大题轻做
- 把功能交付拆成过多文件/函数级小任务
- 文档不足导致中断难以恢复
- 实施过快导致范围失控

## 判定原则

任务规模不只由“代码行数”决定，还由以下因素共同决定：

- 目标是否清晰
- 影响范围是否单一
- 是否跨多个模块
- 是否涉及架构或接口边界
- 是否需要跨会话推进
- 是否存在明显风险或不确定性
- 是否需要正式记录决策、计划或验证
- 是否需要真实入口、真实依赖、真实数据源或公开契约来证明完成
- 是否需要扩展文档承载专题方案、详细设计或契约

## Small Task

### 典型特征
满足大部分以下条件时，可判定为 small：

- 目标清晰
- 影响范围小
- 只涉及 1 个文件或少量文件
- 不涉及架构调整
- 不需要专门设计文档
- 可在一个连续会话中完成
- 风险较低
- 不需要大量状态恢复

### 典型示例
- 修复一个小 bug
- 修改一个函数行为
- 增补一两个测试
- 更新一小段文档
- 轻微重构一个局部函数

### 默认流程
- `/ark:ark-intake`
- `/ark:ark-implement` 或 `/ark:ark-debug`
- `/ark:ark-test`
- `/ark:ark-validate`

### 最低要求
- 至少明确目标
- 至少有验证说明
- 如修改有风险，补最小回归测试
- 不需要为了单点改动强行生成 tasks.md；如已经有 tasks.md，也不要把文件/函数步骤拆成多个 task

## Medium Task

### 典型特征
满足部分以下条件时，可判定为 medium：

- 目标基本清晰，但需要分步骤执行
- 影响多个文件或一个模块
- 需要一定技术设计或结构说明
- 可能需要建立最小真实运行闭环
- 需要跟踪阶段进展
- 可能跨会话继续
- 需要显式验证策略
- 有一定实现风险，但仍可控

### 典型示例
- 给已有模块增加一个完整功能
- 中等规模重构
- 替换某个内部组件
- 增强配置体系
- 引入一项新的基础能力但不改变整体架构

### 默认流程
- `/ark:ark-intake`
- `/ark:ark-plan`
- `/ark:ark-design`（如需要）
- `/ark:ark-solution`（如需要专题方案、契约、集成或数据源说明）
- `/ark:ark-implement`
- `/ark:ark-test`
- `/ark:ark-validate`

### 推荐 Artifact
- `docs/ark/plan.md`
- `docs/ark/validation.md`
- 如结构复杂，补 `docs/ark/design.md`
- 如需要专题细节，补项目自有扩展文档（由 `/ark:ark-solution` 写入）
- 如需持续跟踪，补 `docs/ark/tasks.md`

Medium 任务的 `tasks.md` 默认按功能交付单元或可验证技术闭环拆分。一个自然功能的文件创建、函数实现、配置补充和测试断言应作为同一 task 的实施要点，而不是多个独立 task。

## Large Task

### 典型特征
满足任意多项以下条件时，通常应判定为 large：

- 目标较复杂或仍有较多不确定性
- 涉及多个模块或多个阶段
- 可能改变架构、接口或工程组织方式
- 任务会跨多个会话甚至多个阶段推进
- 需要记录重要决策
- 存在较高风险或高成本返工风险
- 需要完整恢复能力
- 需要长期可追踪的状态面
- 涉及真实基础设施、真实数据、外部契约或多子系统联调

### 典型示例
- 新项目初始化
- 架构重构
- 多阶段功能建设
- 系统性配置改造
- 对外接口变更
- 长周期研发任务

### 默认流程
- `/ark:ark-intake`
- `/ark:ark-spec`
- `/ark:ark-design`
- `/ark:ark-solution`（按需，用于专题细节）
- `/ark:ark-plan`
- `/ark:ark-tasks`
- `/ark:ark-implement`
- `/ark:ark-test`
- `/ark:ark-validate`
- `/ark:ark-handoff`

### 推荐 Artifact
优先完整使用 7 个核心 Artifact：

- `docs/ark/spec.md`
- `docs/ark/design.md`
- `docs/ark/plan.md`
- `docs/ark/tasks.md`
- `docs/ark/decisions.md`
- `docs/ark/validation.md`
- `docs/ark/handoff.md`

详细方案、契约、数据源元信息等按需放入项目自有扩展文档目录，不计入 7 个核心 Artifact。

Large 任务可以有更多 task，但当前执行窗口仍应收敛到 3-8 个功能交付单元或技术闭环。未来阶段保留摘要，不提前拆成大量远期文件/函数级任务。

## 任务粒度原则

`tasks.md` 中的 task 默认是功能交付单元或可验证技术闭环，不是代码步骤列表。

上游 Artifact 必须保护这一粒度：

- `spec.md` 的验收标准按用户可观察能力、业务闭环、公开契约、真实入口或真实数据结果表达，不写文件/函数级实现步骤
- `design.md` 定义技术边界、模块职责、接口契约和技术闭环建议，不生成文件/函数级执行清单
- `plan.md` 组织阶段推进路径，必须给出建议 task 边界和不建议拆分项，不把推进路径写成文件/函数/配置步骤清单

应作为 task：

- 一个用户可观察能力
- 一个调用方可触发的行为
- 一个公开契约或真实入口的变化
- 一个可独立验收的内部技术能力
- 一个明确 batch 的可交付子闭环

不应默认作为独立 task：

- 新增某个文件
- 新增某个函数、类、配置项或字段
- 补一个导入、helper、参数或局部测试断言
- 只能依赖后续步骤才有意义的中间实现

低层步骤应写入 task 的实施要点。若多个 task 必须连续实现、必须统一测试、无法各自验证，应合并为一个 task 或一个明确 batch。

验证可以聚合：多个 task 可以共享一条 `validation.md` 记录，但必须同属一个功能闭环、同一 batch、同一真实入口或同一公开契约，并明确列出覆盖范围。

## 升级规则

以下情况应考虑把 small 升级为 medium，或把 medium 升级为 large：

### 从 Small 升级
若出现以下任一情况，应至少升级到 medium：

- 改动开始跨多个文件
- 需求存在关键歧义
- 需要多步推进
- 需要显式验证策略
- 需要真实依赖、真实数据或公开契约才能判断完成
- 会话可能中断后继续
- 风险明显高于预期

### 从 Medium 升级
若出现以下任一情况，应考虑升级到 large：

- 出现架构级影响
- 需要正式规格文档
- 需要决策记录
- 任务将持续多阶段
- handoff 和恢复成本显著上升
- 多模块协调成为主要难点
- 真实基础设施、数据源或跨系统契约成为主要风险

## 降级规则

有时可以降低流程强度，但必须谨慎：

### 从 Large 降为 Medium
只有在以下情况同时满足时才可考虑：

- 需求已显著收敛
- 实际改动范围明显小于预期
- 不再需要完整 Artifact 追踪
- 风险已明显下降

### 从 Medium 降为 Small
只有在以下情况同时满足时才可考虑：

- 任务已收敛为单点修改
- 不再需要分步骤执行
- 验证路径清晰且短
- 中断恢复成本很低

## 重要提醒

- 不要因为“想快点写代码”而故意低估任务规模
- 不要因为“想显得规范”而把小任务机械升成大流程
- 任务规模服务于执行效率与可靠性，不服务于形式感

## 一句话判断法

如果一个任务需要你担心“中断后会不会忘”，那它通常已经不是 small。
如果一个任务需要你担心“改错后代价很大”，那它通常至少是 medium。
如果一个任务需要你担心“以后为什么这么做会说不清”，那它通常接近 large。
