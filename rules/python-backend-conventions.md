# Python Backend Conventions

本文件定义 ark 在 Python 后端项目中的默认工程规范。

## 项目结构

推荐默认结构：

- `pyproject.toml`
- `src/<package_name>/`
- `tests/`
- `docs/`

新项目默认使用 `src/` layout。

## 包组织建议

典型包结构可包含：

- `api/`：接口层、传输层、HTTP 层
- `domain/`：核心领域模型与领域逻辑
- `services/`：应用服务、编排逻辑
- `repositories/`：持久化访问
- `config.py`：配置加载与设置定义
- `main.py`：应用入口

并非所有项目都必须有这些目录。只创建当前范围真正需要的部分。

## 配置管理

- 优先通过环境变量与显式 settings 对象管理配置
- 避免在各处零散读取配置
- 配置读取应尽量集中

## 类型标注

- 公共函数和方法应尽量补充类型
- 返回值类型尽量精确
- 避免不必要的 `Any`

## 测试规范

- 默认使用 pytest
- 测试按行为和模块边界组织
- 纯逻辑优先单元测试
- 跨边界的重要行为应有集成测试
- 确认 bug 后，尽量补回归测试

## 异常处理

- 抛出有意义的异常
- 避免静默失败
- 必要时在边界层将底层异常转换为更合适的领域异常

## 日志规范

- 优先结构化、带上下文的日志
- 避免正常流程中过量 debug 噪音
- 不记录敏感信息

## 代码质量原则

- 优先简单、可组合的模块
- 避免过早抽象
- 当重复或复杂度已造成实质性负担时再重构
- 接口保持小而明确

## 可维护性与结构复杂度

### 控制函数复杂度
- 单个函数应优先保持单一职责
- 当分支、循环、异常处理和组装逻辑叠加导致理解成本明显上升时，应优先拆分为辅助函数
- 避免把输入解析、业务判断、错误处理、输出组装长期堆在同一函数中

### 尊重封装边界
- 优先通过公开方法或明确提供的访问接口协作
- 避免在类外直接访问以 `_` 开头的内部成员，除非这是明确约定的内部机制且已在设计层说明
- 若确需访问内部状态，应优先考虑补公开接口或重构协作方式

### 对待重复代码的原则
- 避免复制粘贴式的大段重复实现（15 行以上且结构高度相似）
- 仅当重复已形成实质维护负担时再抽象，不为消除轻微重复而引入更复杂的抽象层
- 若暂不抽取，应说明理由（如避免过早抽象）
- 对中大型、分批实施的任务，重复代码应结合任务整体判断；若当前批次与前序批次形成跨文件重复，应在后续收口批次中统一处理，不得长期保留无主的大段重复实现

## 文档与注释规范

默认注释详细度为 `fastchain-enhanced`。已有项目风格明确时，优先对齐项目既有约定；没有明确约定或风格混乱时，采用 ARK 默认 `fastchain-enhanced` 中文 Google 风格。

### 模块级 docstring 策略

- ARK 默认不主动新增顶部模块级 docstring；新建 `.py` 文件不得以三引号模块 docstring 开头
- 既有项目已有模块 docstring 时可保持原状，除非本次任务明确要求清理或项目约定要求调整
- 模块职责优先通过文件路径、命名、公共类/函数 docstring、必要上方块注释和设计文档表达
- 不为统一风格批量删除无关历史文件中的模块 docstring

### 注释详细度分级

| 等级 | 适用对象 | 要求 |
|------|----------|------|
| L0 无需补充 | 简单私有 helper、一眼可读的薄包装、简单 getter/setter、无业务语义的局部赋值 | 不强制 docstring，不写复述代码的注释 |
| L1 standard | 公共函数、公共方法、pydantic model、dataclass、protocol、API handler、service/repository 方法 | 使用中文 Google 风格 docstring，按需写 `Args:` / `Returns:` / `Raises:` |
| L2 fastchain-enhanced | 核心 service/manager/provider/adapter、配置/日志/Apollo/MySQL/Redis/MinIO/ES 等资源封装、连接池/事务/重试/降级/幂等/缓存 | 类级 docstring 说明职责、存在原因、封装边界、生命周期或协作关系；关键属性写 `Attributes:` |
| L3 架构级说明 | 应用启动链路、资源初始化链路、数据导入链路、任务调度链路、跨模块核心编排逻辑 | 说明运行阶段、不变量、失败语义和分层原因；过长细节应放入 design/solution 文档 |

### Docstring 要求

- 公共类、公共函数、关键方法应具备清晰 docstring
- L2/L3 对象不得只写一句空泛摘要，必须解释“为什么存在”“封装什么边界”“哪些约束不能破坏”
- 公共类 docstring：
  - 第一行用中文概括类的核心职责
  - 第二段说明它为什么存在、封装什么边界、管理什么生命周期或协作关系
  - 复杂类可按需增加“增强特性”“核心设计特点”“设计考量”等中文段落
  - 涉及关键状态、资源或公开属性时，应包含 `Attributes:`，属性说明应解释用途、生命周期或约束
  - `Methods:` 可用于 L2/L3 复杂类，但不强制为所有类列出方法清单
- 公共函数和关键方法 docstring：
  - 第一行用中文概括动作或业务语义
  - 按需使用 `Args:`、`Returns:`、`Raises:`，说明含义、失败条件和边界，不只翻译变量名
  - 复杂函数必须说明核心算法、关键假设、边界条件、性能/并发/外部系统约束
  - 简单私有 helper 可以保持简短，不强制使用完整段落
- 不使用赋值语句后的三引号字符串说明常量、变量、集合、配置项或枚举值；这类变量后置三引号 / attribute docstring 不属于 ARK 默认风格
- 常量、变量或集合说明确有维护价值时，写在定义上方的中文块注释；简单枚举值和显而易见常量不补说明

### 中文标点规则

- 中文 docstring 和中文注释的描述句默认不使用句末中文终止标点
- 禁止在 docstring 摘要、详细描述、`Args:`、`Returns:`、`Raises:`、`Note:`、`Warning:` 的描述行末使用 `。`、`！`、`？`、`；`
- 中文块注释也不使用句末中文终止标点
- 允许在句中使用中文逗号、顿号、冒号和括号
- 工具指令类注释不受此规则影响，例如 `# noqa`、`# type: ignore[...]`、`# pylint: disable=...`、`# fmt: off/on`

### 中文注释要求

- 复杂逻辑、非直观边界、降级策略、性能/并发关键点应补充必要中文注释
- 注释优先解释“为什么这样做”“约束是什么”“风险在哪里”
- 业务解释类注释优先写在相关代码上方，不写解释性尾随注释
- 避免显而易见代码的重复性注释
- 避免过长、装饰性、无信息密度的 docstring 和块注释
- 不为补注释扩大实现 scope；只覆盖本次新增/实质修改代码和关键相邻上下文

## 默认工具链

- `pytest`：测试
- `ruff`：lint + format（替代 flake8、isort、black）
- `pyright`：静态类型检查（typeCheckingMode: standard）
- 提交前应运行 `uv run ruff check --fix . && uv run ruff format . && uv run pyright`

## Review 关注顺序

评审 Python 后端代码时，优先关注：

1. 正确性
2. 失败行为
3. 接口清晰度
4. 可维护性
5. 可测试性
6. 运行安全性

安全、并发、性能在当前改动明显涉及这些维度时提高权重，不默认对所有改动做军规式安全审计。
