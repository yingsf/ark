# Craftsmanship Review

本文件承载 `/ark:ark-review` 的 craftsmanship 审查清单。Craftsmanship 不等于 Finding；除非会影响运行、契约、测试可信度或长期维护风险，否则不要把 craftsmanship 建议伪装成 bug。

## 分级

| Level | 含义 |
|-------|------|
| Upgrade | 明显提升长期质量，建议尽快做 |
| Polish | 小型改进，可以后续整理 |
| Keep | 当前写法合理，不建议为了审美改动 |

## API 设计

检查：

- 调用方是否容易正确使用
- 方法命名是否表达真实业务语义
- 返回值是否稳定、明确、难以误用
- 是否暴露内部可变状态
- 是否有不必要的 async、全局状态或隐式副作用
- 是否存在为了测试而设计的不自然 API
- 默认参数是否让正确范围自然出现，而不是让调用方记住隐藏规则

高手写法倾向于：

- 让正确用法自然出现
- 让误用尽早失败
- 用类型、构造器和封装表达约束
- 避免调用方记住隐藏规则

## 数据边界

检查：

- 输入是否在边界处被复制、校验、规范化
- 内部状态是否和外部输入隔离
- 快照语义是否清楚
- 不可变性是类型保证、结构保证，还是只靠注释
- 输出对象是否天然不包含敏感字段，而不是靠调用方别用

高手写法倾向于：

- 明确支持的数据形态
- 在边界处处理复杂性
- 内部状态不被外部引用污染
- 注释解释取舍，而不是掩盖不稳的实现

## 抽象层次

检查：

- 领域概念是否被表达成清晰对象
- 是否存在过早抽象
- 是否存在重复逻辑可以自然收敛
- 私有 helper 是否真能降低复杂度
- helper 名称是否表达业务语义，而不只是技术动作
- 是否为了看起来高级引入基类、工厂、策略模式或依赖注入容器

高手写法倾向于：

- 少而稳的抽象
- 代码结构贴近业务语义
- 不把简单逻辑包进复杂框架
- 抽象只在降低真实复杂度、减少重复或稳定边界时出现

## 错误语义

检查：

- 失败后系统状态是否可预测
- 错误是否可定位
- 是否区分用户错误、配置错误、系统错误
- 是否保留必要上下文
- 日志是否避免敏感信息
- 空状态是返回空结果、明确错误，还是意外扩大查询范围

高手写法倾向于：

- 失败路径和成功路径一样清楚
- 错误消息能帮助定位
- 不吞异常，不乱抛异常
- 不让调用方猜测状态是否已改变

## 测试质量

检查：

- 测试是否验证行为，而不是验证实现细节
- 测试是否能防止未来回归
- 是否覆盖失败路径和状态不变性
- 是否存在脆弱测试
- 是否有无用 fixture、无用 helper、无用测试模型
- 是否覆盖真实反例，而不只是增加测试数量

高手写法倾向于：

- 用少量高信号测试锁住关键契约
- 测试名表达业务行为
- 失败时能快速定位原因
- 不为覆盖率写低价值测试

## 可读性与维护性

检查：

- 后来者是否能快速建立正确心智模型
- 关键约束是否通过命名、类型、结构自然表达
- 注释是否解释为什么，而不是重复做了什么
- 局部复杂度是否可以降低
- 文件中是否存在无用变量、无用类型、过期注释
- 同一业务规则是否散落在多个地方且容易漂移

## 输出规则

- Craftsmanship 建议不放入 Findings，除非它已经构成明确契约、运行时、测试或维护风险
- 每条建议必须说明是否需要现在做：`Do now: 是 / 否`
- 如果当前写法合理，应输出 Keep，避免为了审查而制造改动
- 纯审美偏好不得影响 Verdict
