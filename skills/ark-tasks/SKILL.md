# /ark-tasks

## 目标
将计划拆解为可跟踪的功能交付单元或可验证技术闭环，在 `docs/ark/tasks.md` 中维护执行状态。

## 前置建议
- 建议先执行 `/ark:ark-plan` 形成阶段规划，再用 tasks 管理细粒度状态

## 适用场景
- 计划需要更细粒度的执行跟踪
- 任务跨多个会话、需要可恢复性
- 存在多个并行或有依赖关系的子问题
- 需要显式管理阻塞项

## 不适用场景
- 任务很小，可以安全地一步执行完成
- 还没有清晰的计划（应先执行 `/ark:ark-plan`）
- tasks 会替代 plan 变成主执行文档（两者职责不同）

## 输入
- `docs/ark/plan.md`、当前仓库状态、项目画像、真实性锚点、已知阻塞项

## 输出
- 结构化任务列表，含状态（Todo / Doing / Ready for validation / Done / Blocked）、优先级、依赖、功能/技术闭环、实施要点、建议验证方式、阻塞解除条件

## 相关 Artifact
- `docs/ark/tasks.md`
- 可引用 `docs/ark/plan.md` 和相关扩展文档

## 工作流
1. 阅读 `docs/ark/plan.md`，理解阶段划分与执行顺序。
2. 识别当前执行窗口：优先拆当前阶段和最近下一阶段，未来较远阶段只保留摘要，不生成几十个远期细碎任务。
3. 将计划步骤拆解为功能交付单元或可验证技术闭环——每个任务应满足粒度标准（见下方）。
4. 为每个任务标注：状态、优先级、依赖关系、功能/技术闭环、实施要点、完成后可观察结果、真实性锚点、真实闭环推进、预期验证等级、建议验证方式、可合并验证范围。
5. 若用户明确提供官方文档、内部规范、历史项目、参考项目、静态分析报告或审查意见等材料，记录为可选「外部依据」；默认外部依据为“无”，不得让没有外部依据的项目背负额外要求。
6. 对 Blocked 任务，必须记录「解除条件」（什么情况下可以继续）。
7. 写入或更新 `docs/ark/tasks.md`。

## 任务粒度标准

**合适的粒度**（每个任务应满足）：
- 有明确的完成信号（做完了知道做完了）
- 可在单次专注工作中完成，或可作为一个明确 batch 的组成部分完成
- 可作为功能交付单元或技术闭环被验证
- 对应用户可观察能力、调用方行为、公开契约变化、真实闭环推进，或一个有独立价值的内部能力
- 能说明与真实入口、真实依赖、真实数据源或公开契约的关系；若无关系，应说明是纯内部整理/文档/测试任务

**默认不单独编号为 task 的内容**：
- 创建某个文件
- 新增某个函数、类、配置项或字段
- 补一个导入、参数、helper 或局部测试断言
- 只能依赖后续步骤才有意义的中间实现

这些低层步骤应写入任务的「实施要点」，而不是拆成独立 task。

**太粗的信号**（需要继续拆分）：
- 任务描述包含「以及」「同时」「还有」
- 预计需要跨多个会话才能完成这一个任务
- 无法判断什么情况下算「完成」
- 任务无法说明何时接入真实锚点，只说"完成核心功能"

**太细的信号**（可以合并）：
- 任务只是一个函数调用或单行修改
- 无法独立验证（必须依赖后续步骤才能判断是否正确）
- 在真实闭环建立前拆出大量只产出占位类/空接口的任务
- 一个自然功能被拆成多个必须连续执行、必须统一验证的文件/函数级任务

## 当前窗口规则

- 默认只展开当前可执行窗口的 3-8 个任务
- 未来阶段可用"后续阶段摘要"记录，不逐条生成远期任务
- 若 tasks 已超过 30 条且真实入口/真实依赖/真实数据/公开契约仍未接入，应停止继续细分，建议回到 `/ark:ark-plan` 或 `/ark:ark-sync` 校准计划
- 对后端、数据/AI、集成类项目，P0 窗口内应尽早包含配置、启动/导入/命令执行、真实依赖连接或真实样例数据验证任务
- 对库/SDK/CLI 项目，P0 窗口内应尽早包含包导入、公开 API/命令执行、契约或文件格式验证任务

## 状态定义

| 状态 | 含义 |
|------|------|
| Todo | 尚未开始 |
| Doing | 当前正在进行 |
| Ready for validation | 实现已完成，等待 `/ark:ark-validate` 记录验证证据 |
| Done | 已完成且已验证，必须引用 validation.md 记录 |
| Blocked | 因依赖或外部条件无法继续，必须记录解除条件 |

## 验证要求
- 每个任务都有明确的完成信号
- 每个任务都应说明完成后可观察结果，以及是否推进真实闭环
- 每个任务都应说明功能/技术闭环和实施要点；低层实现步骤不得默认拆成独立 task
- 每个任务应标注真实性锚点和预期验证等级；纯内部任务可标注"无直接真实锚点"
- 多个强相关任务可共享一条 validation 记录，但必须同属一个功能闭环、同一 batch 或同一真实入口
- 外部依据为可选字段；只有用户明确提供时才要求记录需吸收点、明确不吸收点和使用证据
- Done 任务必须引用 `validation.md` 中的具体验证记录；多个 Done 任务可以引用同一条记录，但该记录必须明确列出覆盖任务和覆盖原因
- Blocked 任务必须有解除条件
- tasks.md 应与 plan.md 保持阶段对齐（不应出现 plan 中没有的阶段）
- 不得一次性生成大量远期细碎任务，使真实基础设施、真实数据或公开契约接入被排到很后面
- 执行本 Skill 期间不得写入实现代码（只产出 docs/ark/tasks.md，编码由 `/ark:ark-implement` 负责）
- 不得修改 `docs/ark/tasks.md` 以外的核心 Artifact

## 停止条件
- 当前范围内的所有任务都已被识别并分配了状态
- Blocked 项的解除条件已明确
- `docs/ark/tasks.md` 已完成写入
- 本 Skill 到此停止，输出建议下一步，不继续执行实现代码

## 固定输出格式

写入 `docs/ark/tasks.md`，任务按状态分组：Done → Ready for validation → Doing → Todo → Blocked

每条任务格式：
```
- [ ] T{id} {任务描述}
  优先级：P0 / P1 / P2
  依赖：T{id}, T{id}（无依赖则省略）
  功能/技术闭环：本任务交付什么用户可见能力、调用方行为、公开契约变化或内部技术闭环
  实施要点：文件/函数/配置/测试等低层步骤摘要；不把这些步骤单独编号为 task
  完成信号：什么情况下算这个任务完成（必填）
  完成后可观察结果：用户或维护者能看到什么变化
  真实性锚点：真实入口 / 真实依赖 / 真实数据源 / 公开契约 / 无直接锚点
  真实闭环推进：推进了什么真实入口 / 依赖 / 数据 / 契约；若无则说明原因
  预期验证等级：L0 / L1 / L2 / L3 / L4 / L5
  建议验证方式：命令 / 手工观察 / 契约检查 / 集成验证 / 暂不可验证（说明原因）
  可与哪些任务合并验证：T{id}, T{id} / 无
  仍未覆盖：本任务完成后仍缺少的验证或真实条件
  下一步需要用户提供：无 / 配置 / 样例数据 / 凭据 / 审查意见 / 其他
  外部依据：无 / 官方文档 / 内部规范 / 历史项目 / 参考项目 / 静态分析报告 / 用户审查意见
  需吸收点：...（仅外部依据非“无”时）
  明确不吸收点：...（仅外部依据非“无”时）
  使用证据：...（仅外部依据非“无”且已使用时）
  当前批次：Batch n/m（{批次摘要}）（仅大型任务，无批次时省略）
  验证：validation.md #{章节}（Done 任务必填；可与同闭环任务共享同一记录；Ready for validation 可写待验证方式）
  阻塞原因：...（仅 Blocked 任务）
  解除条件：...（仅 Blocked 任务）
```

## 建议
任务分解完成后，建议下一步为 `/ark:ark-implement`（从第一个 Todo 任务开始实施）。

## 日期要求

- 写入或更新 `docs/ark/tasks.md` 时，头部 `last-updated` 使用当前会话真实日期
- 同一天多次更新任务列表时，`last-updated` 保持当天日期，不得递增为未来日期
- `last-updated` 不是任务版本号；任务状态变化应通过状态分组、任务字段和验证引用表达

## 备注
`docs/ark/tasks.md` 回答「当前有哪些任务及其状态」，不应替代 plan 成为主执行文档，也不应包含需求定义或验证结论。
