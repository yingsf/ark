# /ark-spec

## 目标
将用户请求整理为明确的需求规格，并写入 `docs/ark/spec.md`。规格必须足以支撑 design 或 plan 的编写——含糊的验收标准等于没有规格。

## 前置建议
- 如果需求描述存在歧义或范围不清晰，建议先执行 `/ark:ark-intake` 澄清任务
- 如果 `/ark:ark-analyze` 已预填充 spec 内容，应审查确认现有内容，在此基础上补充完善，而非从零开始

## 适用场景
- 需求需要成文化
- 需要明确验收标准
- 需要显式区分范围与非目标
- 较大任务需要稳定的书面目标

## 不适用场景
- 请求非常小且已完全具体，spec 文档属于明显过度
- 当前缺的是技术设计，而不是需求规格

## 输入
- 用户请求、领域背景、约束条件、已知验收预期
- 项目画像与真实性锚点（如 `CLAUDE.md` 或 analyze 输出已有）

## 输出
- 背景、核心命题与不变量、目标、范围、非目标、价值、约束、验收标准（checklist）、开放问题

## 相关 Artifact
- `docs/ark/spec.md`

## 工作流

### 步骤一：输入源检测

执行后续步骤前，先判断是否有足够的输入：

| 条件 | 动作 |
|------|------|
| 用户提供了输入（命令后有文字） | 正常执行后续步骤 |
| 无输入，`docs/ark/spec.md` 有实质性内容 | 概述现有内容，默认按审查补充模式工作。如需重写，由用户明确指出 |
| 无输入，`docs/ark/spec.md` 无实质性内容 | 停止，告知用户需要提供需求描述，或建议 `/ark:ark-intake` |

**"实质性内容"判定**（满足任一即可）：
- 已包含明确的能力边界或范围描述
- 已包含 analyze 预填充且不只是模板占位注释
- 已有 2 个以上非模板章节被填充

实质性内容的具体判定规则见 `${CLAUDE_PLUGIN_ROOT}/rules/artifact-placeholder-policy.md`。仅包含版本头、`YYYY-MM-DD`、`待填写`、示例编号、状态选项或注释说明时，必须视为初始模板内容。

### 后续步骤

2. 用面向需求的语言重述问题（不要加入技术实现细节）。
3. 提炼核心命题与不变量：识别本项目或本次工作的产品精髓、业务闭环、公开 API、命令契约、数据/AI 评估闭环或 Claude 插件宿主约束；若用户表达了“精髓、核心、灵魂、不要拆、统一、组合能力、全量需求”等信号，必须先固化这一节。
4. 明确什么算成功——用可验证的语言表达，而不是「系统运行良好」。
5. 区分本次范围与非目标：非目标必须真正起到缩小歧义的作用，不要写显而易见的废话。
6. 记录关键约束（技术、时间、兼容性、环境）。
7. 识别真实性要求：本需求是否必须通过真实入口、真实依赖、真实数据源或公开契约才能验收；若不需要，也要说明原因。
8. 编写验收标准——每条必须满足：可观察、可判断、有明确成功条件；涉及真实依赖或数据时必须写明保真度要求。
9. 验收标准必须按用户可观察能力、业务闭环、公开契约、真实入口或真实数据结果表达；不得写成文件、函数、类、配置项或实现步骤。
10. 显式记录尚未解决的开放问题，不要把它们埋在模糊表述里。
11. 写入 `docs/ark/spec.md`。

## 验证要求
- 每条验收标准必须可观察、可判断（「功能正常」不算）
- 验收标准必须保持用户/业务/契约视角，不得写成文件级、函数级、类级、配置项级或其他实现步骤
- 若需求天然是内部能力，验收标准也必须描述它支撑的功能结果或技术闭环
- 核心命题与不变量必须足够具体，能帮助后续 design / plan / tasks 判断是否弱化了需求；若无特殊核心命题，也要说明本次工作的主要不变量
- 非目标必须真正起到缩小歧义的作用
- 规格不应包含实现细节（那是 design 的职责）
- 涉及基础设施、数据、外部系统或公开契约的需求，验收标准必须说明真实验证要求或替身边界
- 不得把数据内容写入 spec；只可记录数据源元信息和验收所需样本范围
- 无用户输入时，不得在 spec.md 无实质性内容的情况下自行生成规格
- 不得修改 `docs/ark/spec.md` 以外的核心 Artifact（如 design.md、plan.md 等）；若设计也需要更新，应建议用户显式执行 `/ark:ark-design`

## 停止条件
- 规格足以支撑 design 或 plan 的编写
- 判断依据：拿着 spec 能判断一个实现方案「在不在范围内」

## 固定输出格式

写入 `docs/ark/spec.md`，结构参考模板：
- 背景 → 核心命题与不变量 → 目标 → 范围 → 非目标 → 用户/业务价值 → 约束 → 真实性与数据要求 → 验收标准（checklist）→ 开放问题

## 建议下一步

- 若设计也需要更新 → `/ark:ark-design`
- 若需要专题方案、接口契约、集成或数据源元信息 → `/ark:ark-solution`
- 若需要拆解实施步骤 → `/ark:ark-plan`
- 若计划非常简单（1-2 步）且无需状态追踪 → `/ark:ark-implement`
- 否则 → `/ark:ark-plan` → `/ark:ark-tasks` → `/ark:ark-implement`

## 备注
不要把重要开放问题埋在模糊表述里。验收标准是 spec 最核心的产出，写好它比写全其他节更重要。
